## 1. 项目概述

### 1.1 定位

企业级 **RAG（Retrieval-Augmented Generation，检索增强生成）知识库问答系统**。
将企业内部文档（TXT / Markdown / PDF / Word / Excel / PPT）自动切片、向量化入库，
再以「检索 + 大模型生成」的方式提供可溯源的智能问答，并提供知识库全生命周期管理。

### 1.2 核心能力

| 能力 | 说明 |
| --- | --- |
| 多格式文档解析 | txt、md、pdf、doc、docx、xlsx、pptx、odt、rtf |
| 自动切片 | 按 token 切分，参数可按中文调优 |
| 向量检索 | 语义相似度召回，可调 topK / 阈值 |
| 增强生成 | 检索片段注入 Prompt，由大模型作答 |
| 引用溯源 | 返回命中的知识片段与相关度 |
| 多轮对话 | 会话级上下文记忆，窗口可配 |
| 流式输出 | SSE 打字机效果 |
| 知识库管理 | 上传 / 增量加载 / 全量重载 / 按来源删除 / 状态查询 |
| 持久化 | 向量库与会话记忆落盘，重启不丢 |

### 1.3 与「裸调大模型」的区别

| 维度 | 直接调大模型 | 本系统（RAG） |
| --- | --- | --- |
| 知识来源 | 模型预训练参数 | 企业私有文档 |
| 时效 | 受训练数据截止限制 | 文档更新即生效 |
| 幻觉 | 容易编造 | 受检索片段约束，无依据时明确说明 |
| 可溯源 | 不可 | 返回引用来源与相关度 |
| 成本 | 长 Prompt 成本高 | 只注入相关片段 |

## 4. 核心流程设计

### 4.1 知识入库流程（ETL）

```
资源收集 allResources()
   ├─ 配置声明 (classpath:doc/xxx)          → origin = "配置"
   ├─ 文档目录扫描 ./data/docs/*            → origin = "目录"
   └─ 按文件名去重 (LinkedHashMap)
              │
              ▼
       createReader(resource, filename)
       ├─ .pdf              → PagePdfDocumentReader
       ├─ .doc/.docx/...    → TikaDocumentReader
       └─ 其他              → TextReader
              │
              ▼
       enrich() 补充元数据
       source / type / loadedAt
              │
              ▼
       TokenTextSplitter.apply()
       按 token 切分为 Document 列表
              │
              ▼
       deleteBySource(source)     ← 幂等：先清旧
              │
              ▼
       vectorStore.write(chunks)   ← 触发 embedding 调用
              │
              ▼
       persist()  → ./data/vector-store.json
```

### 4.2 加载策略

| 模式 | 参数 | 行为 | 适用场景 |
| --- | --- | --- | --- |
| 增量 | `force=false`（默认） | 只处理 `loadedSources` 中不存在的新来源 | 日常启动、新增文档 |
| 全量 | `force=true` | 重载全部来源（写入前先按来源删除） | 文档内容更新、参数调整 |

**为什么全量重载不会产生重复向量**：每次 `load()` 写入前都会执行
`vectorStore.delete(FilterExpressionBuilder.eq("source", filename))`，
即「先删后写」，保证同一来源在向量库中始终只有一份。

### 4.3 RAG 问答流程

```
用户提问 msg + sessionId
        │
        ▼
ChatClient.prompt().user(msg)
        │
        ├─► MessageChatMemoryAdvisor.before()
        │     从 ChatMemory 读取该会话历史，拼进 Prompt
        │
        ├─► QuestionAnswerAdvisor.before()
        │     ① 用 EmbeddingModel 将问题向量化
        │     ② vectorStore.similaritySearch(SearchRequest(topK, threshold))
        │     ③ 召回片段拼进系统消息（含 source 标注）
        │
        ▼
   ChatModel (qwen-plus) 生成答案
        │
        ├─► MessageChatMemoryAdvisor.after()
        │     将本轮问答写入 ChatMemory（窗口上限 maxMessages）
        │
        ▼
   返回 content（阻塞）或 Flux<String>（流式）
```

### 4.4 流式输出

- 接口：`GET /rag/ask/stream`，`produces = MediaType.TEXT_EVENT_STREAM_VALUE`
- 返回：`Flux<String>`（Spring MVC 支持响应式返回值，底层由 Reactor 驱动）
- 前端通过 `fetch` + `ReadableStream` 逐行解析 `data:` 前缀，实现打字机效果
- 同样经过 `QuestionAnswerAdvisor` 与记忆 Advisor，能力与非流式一致

### 4.5 多轮对话记忆

```
MessageWindowChatMemory (maxMessages=10)
        │
        ▼
FileChatMemoryRepository  ← 自定义实现 ChatMemoryRepository
        │
        ▼
./data/chat-memory.json
  行格式：conversationId|role|base64(text)
```

- 按 `conversationId` 隔离会话
- 窗口淘汰：超过 `maxMessages` 自动丢弃最早消息
- Base64 编码规避换行/分隔符转义问题，零第三方序列化依赖

## 5. 数据模型与持久化

### 5.1 Document（知识片段）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | String | 自动生成 |
| `text` | String | 切片后的文本 |
| `metadata.source` | String | 来源文件名（用于过滤/删除） |
| `metadata.type` | String | 扩展名（txt/pdf/docx…） |
| `metadata.loadedAt` | String | 入库时间 |
| `score` | Double | 检索时带回的相关度 |

### 5.2 持久化方案

| 数据 | 方案 | 文件 | 时机 |
| --- | --- | --- | --- |
| 向量库 | `SimpleVectorStore.save/load` | `./data/vector-store.json` | 启动加载、入库后保存 |
| 会话记忆 | 自定义 `FileChatMemoryRepository` | `./data/chat-memory.json` | 每次对话写入后 |
| 上传文档 | 原始文件 | `./data/docs/` | 上传时 |

> **生产建议**：`SimpleVectorStore` 为全内存实现，数据量超过万级片段后内存与检索性能会成为瓶颈，
> 应替换为 PGVector / Milvus / Redis，`VectorStore` 接口无需改动业务代码。

### 5.3 文件持久化格式

向量库：Spring AI 内置的 JSON 序列化（含 id、text、metadata、embedding 数组）。

会话记忆（自定义，规避依赖）：
```
default-001|user|5Y2h5ZWK5L2c5L2/55So...
default-001|assistant|5Y2h5ZWK5L2c5L2/55So...
```

### 6.4 异常映射

`GlobalExceptionHandler` 沿异常链（含 cause）识别故障并给出可操作提示：

| 识别条件 | 返回提示 |
| --- | --- |
| `401` / `api key` / `unauthorized` | 模型服务鉴权失败，请配置 API Key |
| `404` / `not found` | 检查 base-url 与模型名称 |
| `400` / `invalid_request` | 检查模型名称或请求参数 |
| `quota` / `insufficient` | 额度不足，检查账户余额 |

> 生产环境默认关闭，避免泄露内部信息。

## 7. 关键设计决策

### 7.1 幂等加载（先删后写）

**问题**：重复调用加载接口会导致同一内容多次入库，检索时重复召回、浪费 token。

**方案**：以「来源文件名」为维度，写入前先 `delete(eq("source", filename))`，
并维护 `loadedSources` 集合支持增量跳过。

**收益**：加载接口可安全重复调用；文档更新后重载即可覆盖旧内容。

### 7.2 启动期加载失败不阻断启动

`KnowledgeBaseInitializer` 实现 `ApplicationRunner`，捕获全部异常：

```java
if (!StringUtils.hasText(apiKey)) { log.warn(...); return; }   // 无密钥直接跳过
try { loader.loadAll(); }
catch (Exception e) { log.error("...可通过管理接口重试"); }
```

**理由**：模型服务不可用时，应用本身仍应可启动、可运维（能调管理接口重试）。

### 7.3 元数据驱动的管理能力

入库时统一注入 `source` / `type` / `loadedAt`，使得：
- 可按来源过滤检索（多租户/多部门场景可扩展）
- 可按来源精确删除
- 页面可展示每个文档的入库状态与来源

### 7.4 统一来源视图

`listSources()` 合并「配置声明 + 文档目录 + 向量库已入库」三类来源，
避免上传的文档只存在于向量库而在列表里「看不见」的不一致问题。

### 7.5 管理接口鉴权

`AdminAuthInterceptor` 拦截 `/rag/admin/**`：
- `app.rag.auth-token` 为空 → 开发模式放行（并打 WARN）
- 非空 → 要求 `X-Admin-Token` 完全一致，否则 401

设计为「自设共享密钥」，不依赖任何外部平台签发。

### 7.6 前端免构建

单文件 `static/index.html`，Vue 3 + Element Plus 通过 CDN 引入，
由 Spring Boot 静态资源机制托管于 `/`，无需 Node / Vite 工具链。

## 12. 踩坑手册

### 12.1 in-DOM 模板自闭合标签陷阱 ★

**现象**：图标显示、紧随其后的文字全部消失（菜单名、按钮文案、卡片标题）。

**原因**：HTML 规范中只有 void 元素（`br`/`img`/`input`/`meta`/`link`）支持 `<foo />`。
`<svg-icon />` 被解析为**未闭合的开始标签**，后续兄弟节点被吞为其子节点，
而组件模板无 `<slot>`，内容被丢弃。`<el-input />` 等同理，会吞掉后续按钮。

**解决**：
1. 组件外层改为 `<span>` 包裹并暴露 `<slot></slot>`（一处改动覆盖全部调用点）
2. Element Plus 组件一律显式闭合 `<el-input ...></el-input>`

### 12.2 接口根地址尾部斜杠 → 双斜杠

**现象**：`NoResourceFoundException: No static resource ... for request '//rag/...'`

**原因**：`apiBase` 填了 `/` 结尾，拼接后产生 `//rag/...`，路由匹配失败并回退到静态资源处理器。

**解决**：`url()` 中 `replace(/\/+$/, '')` 规范化；同源访问直接留空。

### 12.3 IDE 启动读不到终端 export 的环境变量

**现象**：终端 `export DASHSCOPE_API_KEY=xxx` 后，IntelliJ 启动仍报鉴权失败。

**原因**：IntelliJ 启动的 JVM 与终端 shell 是独立环境。

**解决**：优先使用 `application-local.yml`（无需环境变量）；
或在 Run/Debug Configurations → Environment variables 中配置。

### 12.4 IDE 报 `cannot resolve TikaDocumentReader`

**现象**：Gradle 命令行编译通过，IntelliJ 却报无法解析。

**原因**：IDE 项目模型未同步新依赖。

**解决**：Gradle 工具窗口 → 刷新（或 File → Reload Gradle Project）。

### 12.5 专属端点与公共端点混淆

**现象**：配置密钥后仍报 404 / 连接失败。

**原因**：控制台显示的专属部署端点（`llm-xxx.cn-beijing.maas.aliyuncs.com`）
与公共端点（`dashscope.aliyuncs.com`）不同，且专属实例未必部署了向量模型。

**解决**：在 `application-local.yml` 显式配置 `base-url`，并确认该端点已部署对应模型。

### 12.6 静态资源更新未生效

**现象**：修改 `index.html` 后页面无变化。

**解决**：`Cmd + Shift + R` 强制刷新；必要时 IntelliJ 执行 Rebuild Project 同步资源。
