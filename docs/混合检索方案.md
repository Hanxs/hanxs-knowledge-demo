# 混合检索方案（PG 原生全文检索 + 向量 + RRF）

在 [PgVector 迁移](./PgVector迁移方案.md) 基础上引入第二路召回，
用 RRF（Reciprocal Rank Fusion，倒数排名融合）合并排序。

## 1. 设计

```
用户问题 q
  │
  ├─ 第一路 · 向量
  │     PgVectorStore.similaritySearch(topK=10)
  │     → 余弦相似度召回，擅长语义相近
  │
  ├─ 第二路 · 关键词
  │     JDBC 直查 PG：
  │       to_tsvector('simple', content) @@ tsquery        —— FTS 通道（GIN 索引）
  │       OR content ILIKE '%...%'                          —— 子串通道（pg_trgm GIN）
  │     → 擅长精确词 / 条款序号 / 错误码
  │
  └─ RRF 融合
        score(d) = Σ_r 1 / (k + rank_r(d))    k=60，rank 从 1 开始
        → 重排 → 取 Top-5 送入大模型
```

### 为什么不用 VectorStore 抽象统一做

Spring AI 的 `VectorStore` 只定义了语义检索能力，`similaritySearch` 内部
只能按 embedding 距离排序，无法表达 `@@`（tsvector 匹配）这类谓词。
关键词路必须触达 PG 原生 SQL，所以单独用 `JdbcTemplate` 实现。

### 为什么用 RRF 而不是加权求和

| | 加权求和 | RRF |
| --- | --- | --- |
| 输入 | 需要两路分数可加 | 只要排名 |
| 量纲 | 余弦相似度 0~1 与 `ts_rank_cd` 0~1 不可比 | 与分数无关，天然免疫 |
| 换 Embedding 模型 | 权重失效，要重调 | 无需调整 |
| 效果 | 调好了更好 | 稳定，几乎免调参 |

代价是丢掉了分数里的强度信息（第 1 名和第 2 名的差距被压平），
对 RAG 这种"只要把对的文档放进上下文"的场景，这个代价很小。

## 2. 数据库侧改动

`scripts/pgvector-init.sql` 第 5 节新增两条索引：

```sql
CREATE INDEX IF NOT EXISTS idx_vector_store_content_fts
    ON public.vector_store USING gin (to_tsvector('simple', content));

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX IF NOT EXISTS idx_vector_store_content_trgm
    ON public.vector_store USING gin (content gin_trgm_ops);
```

已有老库升级时单独执行这两段即可（均带 `IF NOT EXISTS`，可重复跑）。

## 3. 关键实现点

### 3.1 中文分词：朴素的 tsvector 方案会失效

PostgreSQL **没有内置中文分词器**。`simple` 配置按空格/标点切词，
一段没有空格的中文会整体变成一个大词元：

```sql
SELECT to_tsvector('simple', content) FROM vector_store LIMIT 1;
-- '为规范公司考勤管理':5 '本制度适用于公司全体在职员工':12 ...
```

对应地，查询永远落在别的词元上：

| 查询 | `@@ plainto_tsquery` | `ILIKE` |
| --- | --- | --- |
| `考勤管理制度` | **0 行** | 1 行 |
| `Updates were rejected` | 1 行 | 1 行 |

所以 `KeywordDocumentSearchService` 用**双通道谓词取并集**：

- **FTS 通道**：`to_tsvector('simple', content) @@ tsquery`，走 GIN 索引，
  对英文 / 数字 / 代码标识符有效，且能通过 `ts_rank_cd` 给出真正的相关度；
- **子串通道**：`content ILIKE '%query%'`，走 pg_trgm GIN 索引，为中文兜底。

打分用一个把两者放到同一量纲的启发式：

```sql
score = ts_rank_cd(...) + least(子串命中次数, 10) * 0.02
```

中文场景 `ts_rank_cd` 恒为 0，靠子串命中次数仍能排出先后。

彻底解决的方向：装 `zhparser` / `pg_jieba`，把 `app.rag.hybrid.fts-config`
改成对应配置名，再关掉 `substring-fallback`。

### 3.2 tsquery 的 AND 语义过严

`plainto_tsquery` 生成的是 AND（多词全命中），检索场景漏召回明显。
默认开启 `query-or-expansion`，把 `&` 改写为 `|`：

```sql
to_tsquery('simple', regexp_replace(plainto_tsquery('simple', :raw)::text, '&', '|', 'g'))
```

`plainto_tsquery` 的输出结构永远是扁平 AND 列表（不会带括号），
所以这个替换是安全的。精度损失由 RRF 再排序兜住。

### 3.3 JDBC 参数必须显式 CAST

踩过的坑：JDBC 传过来的是未知类型的占位符，PG 在下面这些位置无法推断类型，
直接抛 `could not determine data type of parameter`：

```sql
to_tsvector(?, content)        -- ? 需要 CAST AS regconfig
least(int, ?)                  -- ? 需要 CAST AS int
LIMIT ?                        -- ? 需要 CAST AS int
content ILIKE ?                -- ? 需要 CAST AS text
```

因此 SQL 里所有绑定参数都写了显式 `CAST(...)`。

### 3.4 融合主键

`PgVectorStore` 会把数据库主键回填到 `Document#getId()`，
关键词路也 `SELECT id::text`，因此两路可直接按主键对齐。
无 id 的极端情况（自定义 VectorStore 实现）退化为行内容前缀，避免合并成一条。

## 4. 配置项

```yaml
app:
  rag:
    hybrid:
      enabled: true                      # 关闭即退回纯向量检索
      vector-top-k: 10                   # 第一路召回条数
      keyword-top-k: 10                  # 第二路召回条数
      final-top-k: 5                     # 最终送入大模型的上下文条数
      rrf-k: 60                          # RRF 平滑常数
      fts-config: simple                 # 文本搜索配置
      query-or-expansion: true           # AND -> OR
      substring-fallback: true           # 中文 ILIKE 兜底
      substring-token-split: true        # 长句切词后再匹配
      vector-similarity-threshold: 0     # <=0 表示召回阶段不过滤
```

环境变量覆盖：`RAG_HYBRID_ENABLED`、`RAG_HYBRID_VECTOR_TOP_K`、
`RAG_HYBRID_KEYWORD_TOP_K`、`RAG_HYBRID_FINAL_TOP_K`、`RAG_HYBRID_RRF_K`、
`RAG_HYBRID_FTS_CONFIG`。

## 5. 降级策略

以下情况自动退化为纯向量检索，不影响主流程：

| 场景 | 表现 |
| --- | --- |
| `spring.ai.vectorstore.type != pgvector` | `isAvailable()` 返回 false |
| 向量表不存在 | 同上 |
| SQL 报错（缺扩展、语法变化） | catch 后返回空列表，打 WARN 日志 |
| 关键词路 0 命中 | 直接返回向量路结果 |
| 向量路异常 | catch 后返回空列表 |

## 7. 可调性建议

1. **召回太窄**：调大 `vector-top-k` / `keyword-top-k`（它们只是候选池，
   最终条数由 `final-top-k` 决定）。
2. **上下文太长**：调小 `final-top-k`；或调大 `rrf-k` 让排名差异的影响变弱。
3. **中文仍召不回**：内容本身的用词与提问不同，建议启用 `substring-token-split`
   并考虑接入 zhparser。
